# 自动化与分诊 / Automation and Triage

> 这份文档回答一个问题：**本仓库的自动化做了什么、被禁止做什么，以及为什么。**
> This document answers one question: **what this repository's automation does, what it is forbidden to do, and why.**

---

## 一、为什么这份文档比脚本重要

本仓库的立身之本是**可失败性**。正典设有理论失败矩阵，并写明：

> 任何模块达到失败阈值，将被**标记或删除**，而不是被辩护。

自动化最大的风险不是技术故障，而是它**在不知不觉中变成一道把批评挡在门外的过滤器**。
一个自动回复「感谢反馈，已记录」然后静默关闭的机器人，会摧毁这个仓库存在的理由——
而且它失败的方式是安静的，不会有报错，不会有告警。

因此这里先写红线，再写功能。

---

## 二、红线 / Red Lines

以下四条是**硬约束**，任何自动化改动都不得违反：

| # | 红线 | 在哪落实 |
|---|---|---|
| 1 | **不自动关闭任何 issue** | `maintenance.yml` 中 `days-before-issue-close: -1` |
| 2 | **不对理论主张作任何判断**——不判定「成立」「被证伪」「无效」 | `triage.yml` 的 AI 提示词显式禁止；AI 只做归类 |
| 3 | **AI 生成的内容必须自标为机器产物**，并声明以人工判断为准 | 每条 AI 评论带 `🤖 AI 分诊草稿` 标题与免责段 |
| 4 | **未被回复的证伪报告被升级，而不是被清理** | `maintenance.yml` 的 `escalate` 作业，加 `needs-maintainer-review` 标签 |

一句话概括：**自动化做分诊与加速，不做裁决与过滤。**

### 反例：如果违反了会怎样

- 若开启 `actions/stale` 的 issue 自动关闭：一条 90 天无人回复的证伪报告会被静默关闭。
  外界看到的是「这个理论拒绝被检验」——与正典承诺直接矛盾。
- 若让 AI 直接以维护者口吻回复：等于用一个语言模型替理论辩护。
  而本项目的核心主张之一恰恰是**人类必须处在方向性判断的环内**（正典第 19 章 Human Meaning Sovereignty）。
  用 AI 自动回应「意义智能是否成立」的质疑，是自我否定的。

## 三、三个工作流 / The Three Workflows

### 1. `triage.yml` — 事件驱动分诊

触发：issue 被打开或编辑。

| 步骤 | 做什么 | 不做什么 |
|---|---|---|
| 解析表单 | 依据**固定字段名**判定类型（证伪报告 / 缺陷 / 建议） | 不解析语义、不猜测意图 |
| 打标签 | 抓取正文里的 `L1`–`L6`、`H1`–`H18` 并加为标签 | 不据此调整优先级 |
| 完整度提示 | 检查是否含样本与统计、统计功效、对照的预注册证伪标准、可复现信息；缺什么列什么 | **不因为缺字段而拒收**——缺字段是输入不完整，不是主张不成立 |
| AI 分诊（可选） | 输出归类、涉及假设、建议补充 | 不判断成立与否、不建议关闭、不以维护者口吻发言 |

> **为什么完整度检查不是门槛**：本仓库要的是**可检验性**，不是设卡。
> 一条字段残缺的报告仍然可能是对的；我们要做的是帮提交者补齐，而不是让它消失。

### 2. `maintenance.yml` — 每周定时维护

触发：`cron: '17 3 * * 1'`（每周一 03:17 UTC），也可手动触发。

| 作业 | 做什么 |
|---|---|
| `stale` | issue 满 90 天无活动则加 `awaiting-response` 标签并温和提醒；**永不关闭**。PR 满 45 天提醒、30 天关闭（废弃 PR 与未回复的批评性质不同） |
| `escalate` | 找出创建超过 14 天、且**没有维护者回复**的证伪报告，加 `needs-maintainer-review` 标签并写进日志 |
| `digest` | 汇总未关闭 issue/PR 数、证伪报告数、等待回复数、标签分布，追加到固定议题「维护摘要 / Maintenance Digest」 |

`escalate` 的「维护者回复」判定会排除两类评论：机器人自己发的完整度提示与 AI 分诊草稿。
否则机器人提示会被误计为「已回复」。

### 3. `ci.yml` — 已有的构建校验

见仓库根 README。它只验证白皮书与演示系统能否重建，与分诊无关。

## 四、启用 AI 分诊（可选）/ Enabling AI Triage

**默认关闭。** 不配置任何 secret 时，`triage.yml` 的第 3 步整步跳过，其余功能全部照常工作。

要启用，在 `Settings → Secrets and variables → Actions` 添加：

| 类型 | 名称 | 说明 |
|---|---|---|
| Secret | `LLM_API_KEY` | 模型服务的 API key |
| Variable | `LLM_BASE_URL` | 可选，默认 `https://api.deepseek.com`。任何兼容 OpenAI `/chat/completions` 的服务都可 |
| Variable | `LLM_MODEL` | 可选，默认 `deepseek-chat` |

> **提示词是刻意收窄的。** 它把模型限定为「归类器」，并在 system prompt 里逐条列出禁止事项。
> 若你要改这个提示词，请先读第二节的红线——放宽它等于放弃本仓库的诚信承诺。

## 五、标签依赖 / Label Dependency

⚠️ **GitHub 对不存在的标签是「静默丢弃」的**——不报错、不提示、不重试，标签就是不生效。
工作流与 issue 表单都依赖标签，所以这是最容易无声失效的一环。

`tools/publish.py` 在推送时会自动创建下表中的标签（`ensure_labels()`）。
若 token 没有 `Issues: write` 权限，它会打印一份清单让你手动创建，而不是假装成功。

| 标签 | 颜色 | 用途 |
|---|---|---|
| `falsification-report` | `#EF4444` | 证伪报告（issue 表单自动附加） |
| `needs-maintainer-review` | `#F97316` | 超过 14 天无人回复的证伪报告，由 `escalate` 作业添加 |
| `awaiting-response` | `#9CA3AF` | 满 90 天无活动，由 `stale` 作业添加（**只是提醒**） |
| `maintenance-digest` | `#1B3A5C` | 标记累积周报的固定议题 |
| `L1` … `L6` | 各层主题色 | 由 `triage.yml` 依据正文中出现的层号自动添加 |

手动创建入口：`https://github.com/<owner>/<repo>/labels`

> 若你想用只读或最小权限的 token 推送，就无法建标签。
> 此时请务必按上表手工补齐——否则分诊会看起来「在工作」，实际什么都没打上。

## 六、平台限制（不是配置问题）

| 限制 | 说明 |
|---|---|
| **schedule 会在 60 天无活动后停用** | GitHub 的官方行为。仓库静置两个月后，定时任务不再运行，直到有人在 Actions 页面点一次 Enable |
| **cron 不精确** | 高峰期可能延迟数十分钟。不要依赖它做分钟级的事 |
| **仅默认分支生效** | schedule 只在该工作流位于默认分支时触发 |
| **公共仓库 Actions 免费** | 私有仓库会消耗配额 |

## 七、一个自指的注记 / A Self-Referential Note

用 AI 来分诊针对「意义智能」理论的批评，是这个理论自己的问题的一个真实实例。

六层栈的第六层**反思与审视递归**问的是：**谁来审视审视者？**
正典第 19 章把答案落在「人类意义主权」上——方向性判断必须留在人类环内。

所以本仓库的自动化设计本身就是一次小型检验：

> **如果 AI 能替代人类回应「这套理论是否成立」的质疑，那么这套理论关于人类必须留在环内的主张就被削弱了。**
> 我们按「不能替代」来设计——不是因为做不到，而是因为做了就等于反证自己。

这不是修辞。这是把红线写成代码的理由。

## 八、如何修改自动化

1. 改动任一红线（第二节）需要同步修改本文件，并在 PR 描述里说明理由。
2. 改完 YAML 请确认可解析：
   ```bash
   python -c "import yaml,glob; [yaml.safe_load(open(f,encoding='utf-8')) for f in glob.glob('.github/**/*.yml', recursive=True)]"
   ```
3. `triage.yml` 与 `maintenance.yml` 都可用 `workflow_dispatch` 或重新打开一个测试 issue 来验证，
   建议先在 fork 或私有测试仓库里跑通再合并。
